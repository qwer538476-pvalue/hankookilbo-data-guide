02 · 데이터 수집 구조

무엇이 어떻게 다른가

세 시스템은 모두 '웹 데이터를 수집한다'는 점에서 비슷해 보이지만, 수집 시점·방식·목적이 근본적으로 다릅니다. 수치가 왜 다른지 설명하려면 이 차이를 알아야 합니다.

05 · 상호 영향 관계
왜 서로 영향을 미치는가

각 시스템은 독립적으로 보이지만 강하게 연결되어 있습니다. 한 곳의 문제가 다른 곳의 업무에 즉각 영향을 줍니다.

⚡ Tableau 이중 역할 문제

Tableau는 Athena → Data Cloud 파이프라인과 회원 현황 대시보드 역할을 동시에 수행. 파이프라인 이상 시 대시보드도 즉각 영향.

  • Athena→Tableau데이터 호출
  • Tableau→Data Cloud일배치 적재
  • Tableau→대시보드회원 현황 시각화

🔗 join_id 연결 고리

회원번호(join_id)는 Athena와 Salesforce를 잇는 핵심 키. 수집 오류 시 양쪽 동시 역추적 필요.

  • Hmap 2.0→Athenajoin_id 포함
  • Athena↔Salesforce DC연결 필요
  • GA4✕Athenajoin_id 없어 불가

📦 Data Cloud 원본 부재

Data Cloud에 원본 저장소가 없고 CDP에 강제 적재 구조. 오류 발생 시 원본 검증·소급 조회 어려움.

  • Service Cloud→Data Cloud실시간
  • Marketing Cloud→Data Cloud발송이력 변환
  • 원본 없음→소급 검증 불가

📋 전략실 3팀 협업 구조

AI&데이터팀, 통합멤버십팀, DB저작권팀이 각자 영역에서 데이터 업무를 확장 중이며 각 영역이 서로 맞닿아 있습니다.

  • AI&데이터팀→Athena·행동분석
  • 통합멤버십팀→Salesforce·CRM
  • DB저작권팀→통합DB·메타데이터
구조적 취약점 4가지 — ① Tableau 파이프라인+대시보드 이중 역할 ② Data Cloud 원본 없음 → 소급 불가 ③ Hmap 수집 권한 없음 → 이슈 시 외부 의존 ④ join_id 단절 → Athena·Salesforce 교차 분석 불가

ERD는 데이터베이스 구조를 시각화하는 도구입니다. 그런데 한국일보 데이터 시스템은 ERD가 맞지 않는 구조입니다. 왜 그런지 이해하는 것이 핵심입니다.

📄 ERD란 무엇인가 원본
ERD란
Entity Relationship Diagram

데이터베이스의 테이블 구조와 테이블 간 관계를 시각화한 설계 도구입니다. 여러 테이블이 FK(외래키)로 연결된 관계형 DB 구조에서 의미가 있습니다. 프로젝트 초기 설계 단계에서 데이터 모델러가 작성하고, 개발자·분석가가 참조합니다.

CRUD와의 관계
ERD는 CRUD가 모두 가능한 구조에서 작동

관계형 DB는 Create·Read·Update·Delete 네 가지 작업이 모두 가능합니다. ERD는 이 구조, 즉 여러 테이블이 서로 JOIN되고 데이터를 수정·삭제할 수 있는 환경에서 테이블 간 관계를 표현하는 도구입니다.

왜 한국일보 데이터에는 ERD를 그릴 수 없나
ERD는 여러 테이블이 FK로 연결된 정규화 구조에서 의미가 있습니다. GA4·Athena는 단일 이벤트 테이블에 모든 데이터가 flat하게 쌓이는 구조라 ERD를 그리면 테이블 하나에 화살표 없는 그림이 나옵니다. 테이블 간 JOIN 관계 자체가 없기 때문입니다.
GA4 — 이벤트 트래킹 구조

유저 행동을 이벤트 단위로 수집합니다. 페이지뷰·클릭·스크롤 모두 event_name 컬럼으로 구분되며, 관계형 구조가 아닌 이벤트 스트림 형태로 쌓입니다.

이벤트 구조는 3차원 형태

일반 RDB는 행·열로 이루어진 2차원 구조입니다. GA4·Athena의 event_params는 컬럼 하나 안에 key-value 쌍이 또 쌓이는 중첩 구조입니다. 그래서 일반 SQL로 바로 꺼낼 수 없고 UNNEST로 펼쳐야 합니다.

컬럼 정의서가 더 적합한 이유

컬럼 정의서가 ERD 기능을 못 내는 게 아닙니다. 애초에 이벤트 구조는 테이블 간 JOIN 관계가 없기 때문에 ERD가 필요 없는 구조입니다. event_name별 컬럼 정의서가 이 구조에 가장 적합한 문서 형태입니다.

문제 1 / 5
Athena(Hmap 2.0)와 GA4의 수집 시점 차이로 인해 발생하는 실질적인 차이는?
AAthena는 회원 데이터도 수집하지만 GA4는 행동 데이터만 수집한다
BGA4는 새 탭 클릭이나 외부 링크 이동 시 데이터가 누락될 수 있지만, Athena는 클릭 순간 수집되므로 누락이 없다
C두 시스템은 수집 방식이 동일하며 수치가 다른 이유는 서버 오류 때문이다
DGA4가 더 정확하기 때문에 Athena는 보조 지표로만 활용한다
정답: B — GA4는 페이지가 실제로 로드되어야 수집됩니다. Athena(Hmap 2.0)는 클릭 순간 수집되어 페이지 이동 여부와 무관하게 적재됩니다. 어느 쪽이 더 정확하다고 단정할 수 없으며, 수집 목적과 방식이 다릅니다.
문제 2 / 5
GA4·Athena 데이터 구조에 ERD를 적용할 수 없는 가장 근본적인 이유는?
AGA4와 Athena는 데이터 용량이 너무 커서 ERD 툴이 처리할 수 없기 때문이다
BGA4·Athena는 단일 이벤트 테이블에 데이터가 flat하게 쌓이는 구조라 테이블 간 FK 연결 관계 자체가 없기 때문이다
CERD는 구글 클라우드 서비스와 호환되지 않는 도구이기 때문이다
D한국일보 데이터팀에 ERD를 그릴 수 있는 전담 인력이 없기 때문이다
정답: B — ERD는 여러 테이블이 FK로 연결된 정규화 구조에서 의미가 있습니다. GA4·Athena는 모든 데이터가 단일 이벤트 테이블에 append-only로 쌓이는 구조라 테이블 간 JOIN 관계 자체가 없습니다. ERD를 그리면 테이블 하나에 화살표 없는 그림만 나옵니다. 이 구조에는 event_name별 컬럼 정의서가 적합합니다.
문제 3 / 5
BigQuery는 GA4와 어떤 관계이며, Athena와의 결정적인 차이는?
ABigQuery는 Athena의 백업 저장소이며, 두 시스템 모두 join_id를 포함한다
BBigQuery는 GA4 원시 데이터를 SQL로 조회하는 서비스이며, Athena와 달리 내부 join_id가 없어 Salesforce와 연결이 불가하다
CBigQuery는 Athena보다 더 많은 데이터를 보유하며 두 시스템은 교체 가능하다
DBigQuery는 오직 광고 성과 데이터만 저장하며 행동 분석에는 활용하지 않는다
정답: B — BigQuery는 GA4 원시 데이터를 SQL로 조회하는 구글 클라우드 서비스입니다. GA4 화면과 달리 이벤트 단위 원시 데이터 조회가 가능하지만, 내부 join_id가 없어 Athena나 Salesforce와의 직접 연결은 불가합니다.
문제 4 / 5
Tableau가 "구조적 문제"로 분류되는 이유로 가장 옳은 것은?
ATableau의 라이선스 비용이 너무 비싸기 때문이다
BTableau가 Athena → Data Cloud 데이터 파이프라인 역할과 회원 현황 대시보드 역할을 동시에 수행하여, 파이프라인 이상 시 대시보드도 즉각 영향을 받기 때문이다
CTableau가 Salesforce 데이터만 처리할 수 있어 다른 플랫폼 데이터를 시각화할 수 없기 때문이다
DTableau 서버가 해외에 있어 데이터 전송 속도가 느리기 때문이다
정답: B — Tableau는 Athena → Data Cloud 파이프라인 역할과 Salesforce Data Cloud 기반 회원 현황 대시보드 역할을 동시에 수행합니다. 두 역할이 분리되어 있지 않아 파이프라인에 이상이 생기면 대시보드도 즉각 영향을 받습니다.
